# dsh shim 与 pnpm 打包实施计划

> 状态：**待实施**。本文是落地前的设计与验收清单，不是已完成功能的说明。
> 相关：[桌面客户端架构](desktop-client-architecture.zh.md)、[TODO](../TODO.md)。

## 背景

内置市场插件（`dsh-desktop-safe-market`）的「安全安装 / 安全升级」按钮会生成一段提示词交给 Agent，末尾是官方命令：

```
dsh plugin --profile <profile> add <该仓库 tarball>
```

市场插件自身**不 spawn 任何进程**，安装动作完全依赖 Agent 去执行 `dsh`。而纯桌面用户（未安装 Node / dsh）的 PATH 上没有 `dsh`，这条命令必然失败。

市场 0.2.9 起，提示词不再假定 `dsh` 就在 PATH 上，而是让 Agent 自己按四步定位：① PATH；② dsh 默认安装目录；③ npm / pnpm 全局 bin；④ 正在监听 1466 端口的 dsh 进程，取其可执行文件路径。**这改善了失败的形态，但没有关闭这个洞**——内置运行时下四步全部落空：

- ①②③ 对纯桌面用户本就为空。客户端只往子进程 PATH 追加 `~/.dsh-desktop/bin`，那里只有 `ensureNodeShim()` 写出的 `node`；闭包里的 `dsh-runtime/node_modules/.bin/dsh` 不在 PATH 上。
- ④ 也匹配不上：客户端以 `web --port 0` 启动运行时（`src/main/index.ts`），端口是随机的，不是 1466。

所以 Agent 拿到的从「命令不存在」变成了「四处都找不到」——更像一条诊断，但仍不是能转述给用户的准确结论。

⚠️ 第 ④ 步还藏着一个踩空点：客户端启动的内置运行时，其**可执行文件路径就是客户端自己的 exe**（`spawn(process.execPath, [runtime-launcher.mjs, 'web', '--port', '0'])`）。今天靠随机端口侥幸不匹配；一旦端口固定，Agent 就会去执行 `<客户端 exe> plugin --profile <name> add …`——那不是 dsh CLI，是拉起第二个 Electron 实例。

注意本计划的网关**挡不住这一条**：`dsh-cli.mjs` 只在 shim 这条链路上生效，Agent 直接执行客户端 exe 时它根本不在调用栈里。真正的缓解是 shim 让第 ① 步先命中，Agent 压根走不到第 ④ 步——见第一阶段末尾的收益清单。

更深一层：`dsh plugin` 只是 pnpm 的转发器（`spawnSync("pnpm", ...)`，找不到即打印 `pnpm not found on PATH` 并返回 127），而客户端也不打包 pnpm。所以要让市场真正闭环，缺的是**两样东西**。

客户端已经为「从没装过 Node 的用户也该有 `node`」写了 `ensureNodeShim()`。同样的逻辑对 `dsh` 更成立：**Agent 就运行在 dsh 里面，却唯独调用不了 dsh 自己。**

## 两阶段划分

| | 内容 | 前置 |
| --- | --- | --- |
| 第一阶段 | dsh shim + 启动拦截 | 无 |
| 第二阶段 | 打包 pnpm | 第一阶段 |

两阶段是**严格的依赖关系**：没有 dsh shim，`dsh` 这个名字不在 PATH 上，打包了 pnpm 也用不上。

第一阶段单独落地是有意义的——它带来三类自省能力，并把失败从「命令不存在」变成一条准确、可转述的诊断。但要说明：**第一阶段落地后，市场的第三方插件安装仍然装不上**，那是第二阶段的事。

# 第一阶段：dsh shim + 启动拦截

## 已核实的前提

以下事实来自对内置运行时 `@deepseek-ai/dsh@0.1.0-rc.6` 与本仓库源码的核对，是下面设计的依据：

- `--profile <name>` 是根命令的**必填项**，裸 `dsh` 直接报错——不存在「默认 profile 被误启动」的情况。
- `web` 是子命令别名（等价 `--profile web`）；`plugin` 是子命令，带 `requiredOption('--profile')` 与 `rejectParentOptions`，因此 `plugin` 永远是用户参数的第 0 位。
- `--dump-config` / `--dump-default-config` 可出现在 `dsh --profile web --dump-config` 与 `dsh web --dump-config` 两种位置；二者走 `dump-config` 模块，**不进 cordis boot**。
- `--expose-internals` 只有 profile boot 需要（Electron Node 模式下 `cordis-plugin-hmr` 经 `node-addon-require-builtin` 会报 `--expose-internals is required`）；`--dump-config` 与 `plugin` 不需要。
- `findOnPath()` 对 shim 目录的排除是**按目录**的（`isSameDirectory(dir, shimDir)`），与文件名无关，因此放 `dsh` 进去不会被 `detectDshOnPath()` 误判为「用户自装的 dsh」。且 `findOnPath` 扫的是主进程的 ambient PATH，shim 目录只出现在 `childPath()` 里。
- `childPath()` 是**追加**（append）而非前置，用户自装的 dsh 永远优先。
- 官方 `dsh plugin` 的 `reconcilePlugins` 只摘除 `dependencies` 里的名字；客户端的 in-box 市场座位不写 `dependencies`（只写 `dsh.profile.bundles` + 复制目录 + `.dsh-desktop-seat.json`），**不会被误伤**。

## 设计

### 分层

纯策略 / 网关 / shim 三者分开，照抄 `src/main/runtime-resolution.ts` 已验证的模式：纯决策函数可在任何平台单测，Windows 分支不需要 Windows 机器。

### 现有启动路径零改动

拦截只作用在 shim 这条新链路上：

```
主进程 spawn ──────────────────────────→ runtime-launcher.mjs → dsh bin   (不变)

Agent 的 dsh ─→ dsh-cli.mjs ─(放行)──→ runtime-launcher.mjs → dsh bin
                     └─(拦截)─→ stderr + exit 2
```

### 默认拒绝

分类器只放行**可证明不启动 profile** 的调用，其余一律拦。上游哪天新增启动型子命令，本网关是 fail-closed。

## 变更清单

### 1. `src/main/dsh-cli-policy.ts`（新，纯函数，无副作用）

导出：

```ts
classifyDshInvocation(args: string[]): { allow: true } | { allow: false; reason: string }
```

规则（镜像 commander 语法）：

| 调用形态 | 判定 |
| --- | --- |
| `args[0] === 'plugin'` | 放行（pnpm 转发器，永不启动） |
| 启动器前缀含 `--dump-config` / `--dump-default-config` | 放行（走 dump-config 模块，不 boot） |
| 含 `-V` / `--version` | 放行 |
| 既无 `--profile` 也非 `web` 子命令 | 放行（dsh 自己会报 `--profile is required` 或打帮助，让真错误透出去） |
| 其余（解析为 `mode: "profile"`） | **拦截** |

「启动器前缀」的扫描规则：从头消费已知启动器 token（`--profile <v>`、`--patch <v>`、`--dump-config`、`--dump-default-config`、`-V`/`--version`、开头的 `web`），遇到第一个未知 token 即停——这正是 `passThroughOptions()` + `enablePositionalOptions()` 的语义。这样内层 app 参数里恰好叫 `--dump-config` 的 token 不会被误判成放行。

### 2. `src/main/dsh-cli.ts`（新，网关入口）

```
1. classifyDshInvocation(process.argv.slice(2))
2. 拦截 → process.stderr.write(message) + process.exit(2)
3. 放行 → await import(<同目录>/runtime-launcher.mjs)
```

第 3 步**必须**用计算出的 specifier：

```ts
await import(pathToFileURL(join(dirname(fileURLToPath(import.meta.url)), 'runtime-launcher.mjs')).href)
```

否则 esbuild 会静态解析并内联，导致 `runtime-launcher` 的顶层副作用（读 env、patch `child_process`、import 官方 entry）抢在网关之前执行。

拦截文案（英文，与 dsh 自身的 `dsh:` 前缀风格一致——Agent 要读它）：

```
dsh: this `dsh` comes from DeepSeek Harness Desktop, which is already running
this profile in its own window — booting a second instance would share the
same DSH_HOME. Use the app window instead.
Available here: dsh plugin --profile <name> ..., dsh --profile <name>
--dump-config, dsh --version.
```

退出码 **2**（用法错误），与 dsh 自身的 1 / 127 区分开。

### 3. `src/main/index.ts`：`ensureNodeShim()` → `ensureShims()`

复用同一个 memo、同一个 `binDir`、同一个 try/catch（写失败只 warn，不影响会话）。新增 `dsh` / `dsh.cmd` 两个分支。

POSIX `~/.dsh-desktop/bin/dsh`：

```sh
#!/bin/sh
# Generated by DeepSeek Harness Desktop. The bundled dsh CLI, named `dsh`.
[ -n "$DSH_HOME" ] || DSH_HOME="<childHome>"
export DSH_HOME
DSH_DESKTOP_RUNTIME_ENTRY="<bundledBin>" ELECTRON_RUN_AS_NODE=1 \
  exec "<execPath>" --expose-internals "<resources>/dsh-cli.mjs" "$@"
```

Windows `~/.dsh-desktop/bin/dsh.cmd`：

```bat
@echo off
rem Generated by DeepSeek Harness Desktop. The bundled dsh CLI, named `dsh`.
setlocal
if not defined DSH_HOME set "DSH_HOME=<childHome>"
set "ELECTRON_RUN_AS_NODE=1"
set "DSH_DESKTOP_RUNTIME_ENTRY=<bundledBin>"
"<execPath>" --expose-internals "<resources>\dsh-cli.mjs" %*
exit /b %ERRORLEVEL%
```

三处刻意的选择：

- **`DSH_HOME` 用「仅缺失时补」**，不是无条件 `export`。子进程环境里已经设过 `DSH_HOME: childHome()`，Agent 天然继承；无条件写死会打掉 Agent 显式指定的 `DSH_HOME=x dsh ...`。
- **保留 `--expose-internals`**。v1 拦掉了所有 boot，这个 flag 暂时用不上；但它属于「在 Electron Node 上跑内置 CLI」这件事，与网关策略是两个概念，独立保留可避免将来放宽策略时漏掉。
- **`<bundledBin>` 固定取 `resolveBundledDsh()` 的路径**，不依赖本次选中了哪个运行时。因为 shim 目录追加在 PATH 尾部，用户自装的 dsh 永远优先，这里只是兜底。`resolveBundledDsh()` 返回 undefined 时（构建不带运行时）跳过 dsh shim，node shim 照写。

### 4. 构建与打包

- `package.json` 的 `build:shell` 增加第 4 个 esbuild 入口 → `.build/dsh-cli.mjs`
- `electron-builder.yml` 的 `extraResources` 增加 `.build/dsh-cli.mjs → dsh-cli.mjs`（与 `runtime-launcher.mjs` 并排）

### 5. 门禁

| `scripts/smoke-package.mjs`（扩） | 断言打包产物含 `resources/dsh-cli.mjs` |

## 关于 `headless` 的决定

`dsh --profile headless "..."` 是一次性会话，本身不是长驻服务，但它与 `web` 走同一条 `mode: "profile"` 路径，**v1 一并拦掉**。

理由：`TODO.md` 里的并发运行风险至今未评估，而 headless 同样会写同一个 home 的会话存储。等并发问题评估清楚后，放宽只需在策略里加一个 profile 白名单常量，`--expose-internals` 已经预留。

因此第一阶段的**实际**收益收敛为：

- `--dump-config` / `--dump-default-config` / `--version` 三类自省能力
- 一次准确、可转述的失败（`dsh: pnpm not found on PATH — install pnpm to manage profile plugins`，退出 127），取代 Agent「四处都找不到 dsh」之后的自作主张
- **让市场提示词的定位在第 ① 步就收敛**：`dsh` 进了 PATH 之后 Agent 不再向下试探，走不到第 ④ 步那条「按端口找进程、把客户端 exe 当 dsh 使」的路。这是对该踩空点唯一有效的缓解——网关只覆盖 shim 这条链路，对直接执行客户端 exe 无能为力。这条收益不依赖第二阶段
- 第二阶段的必要前置

## 验收

**必须在真实打包版上跑**——`ensureShims()` 在 `!app.isPackaged` 时直接返回 undefined，dev 环境与 `pnpm run e2e` 覆盖不到这条路径，只能靠 `smoke:package` 与手验兜底。

在 Agent 的 shell 里：

1. `dsh --version` → 打印版本
2. `dsh --profile web --dump-config` → 打印组装后的配置
3. `dsh web` → 拦截文案 + 退出码 2，**且没有新进程监听端口**
4. `dsh --profile web` → 同上（别名不能绕过）
5. `dsh plugin --profile web add foo` → dsh 自身的 `pnpm not found on PATH`，退出 127（证明放行链路通到了真 CLI）
6. `which dsh` / `where dsh` → 指向 `~/.dsh-desktop/bin`
7. 机器上装有真 dsh 时，`dsh --version` 报的是**用户那份**（验证追加而非前置）
8. `--expose-internals` 不产生 stderr 噪音

# 第二阶段：打包 pnpm

## 已实测的可行性

以下都是在本机（Windows 11 / Electron 39.8.10 / Node 22.22.1）实际跑出来的，不是推断：

- **pnpm 在 Electron Node 模式下可用。** `ELECTRON_RUN_AS_NODE=1 electron.exe pnpm.mjs --version` 正常返回。
- **真实安装可以走通。** 在一个仿造的 web profile 目录里执行
  `ELECTRON_RUN_AS_NODE=1 electron.exe pnpm.mjs add <市场 tarball>`（实测用的是当时内置的 v0.2.7）
  → `Packages: +3`，**9.6 秒**完成，装出的 `lib/` 齐全。
- **不需要构建工具链。** 市场插件的 `package.json` 没有 `prepare` 脚本，`lib/` 随 tarball 直接下发，`pnpm-workspace.yaml` 的 `allowBuilds` 里也没有它。一次安装只是「下载 tarball + 从 registry 拉 `yaml`/`zod` 两个小包」。
- **体积代价可控。** pnpm 包 37 MB，其中 `artifacts/exe` 占 18 MB——那是自带 Node 的独立可执行变体，用不上、可裁。实需 `dist/` + `bin/` ≈ **20 MB 未压缩**。

  | 基准 | 现值 | 增幅 |
  | --- | --- | --- |
  | 装机包（压缩后） | 109 MB | +6% |
  | 安装后展开 | 544 MB | +3.7% |
  | 其中 dsh 运行时闭包 | 218 MB | +9% |

## 变更清单

### 1. 闭包接入

- `dsh-runtime/package.json` 增加**精确版本**的 `pnpm` 依赖（与 `@deepseek-ai/dsh` 同样的 pin 策略）。`scripts/prepare-runtime.mjs` 的 `pnpm deploy --prod --frozen-lockfile --node-linker=hoisted` 会自动带上，无需新的打包机制。
- pnpm 自身**无 runtime 依赖**（`package.json` 里没有 `dependencies`），不会污染 dsh 闭包的模块解析。
- `prepare-runtime.mjs` 增加裁剪 `node_modules/pnpm/artifacts` 的规则。

  ⚠️ 该脚本的注释明确写了 *"Matching is by extension only. Pruning conventional directory names is not safe here"*（`yaml` 把运行时代码放在 `dist/doc/` 下，按目录名裁会删掉可执行代码）。因此这条规则必须是**精确相对路径**，不能是目录名匹配。

### 2. pnpm shim

`ensureShims()` 再加 `pnpm` / `pnpm.cmd` 两个分支，入口指向
`<resources>/dsh-runtime/node_modules/pnpm/bin/pnpm.mjs`。

**走 `runtime-launcher.mjs`，不走 `dsh-cli.mjs`。** 理由是 pnpm 会 spawn 生命周期脚本，`ELECTRON_RUN_AS_NODE` 绝不能漏进那些子进程——而 `runtime-launcher` 的语义正好是「从 ambient env 摘掉它，只在 spawn 目标是 `process.execPath` 时补回」。网关是 dsh 专属的策略，与 pnpm 无关。

两处与 dsh shim 的差异：

- **不带 `--expose-internals`**：pnpm 不需要。
- **POSIX 侧必须 `chmod 755`**：`dsh plugin` 在 POSIX 上以 `shell: false` spawn `pnpm`，靠 shebang 直接执行。Windows 侧 `dsh plugin` 用 `shell: true`，靠 `PATHEXT` 找到 `pnpm.cmd`，已经对得上。

### 3. 版本耦合做成红色构建

pnpm 的 `bin/pnpm.mjs` 开头是**硬退出**，不是警告：

```js
} else if (major < 22 || major == 22 && minor < 13) {
  console.error(`ERROR: This version of pnpm requires at least Node.js v22.13 ...`)
  process.exit(1)
}
```

pnpm 11 要求 Node ≥ 22.13，Electron 39 提供 22.22——**余量只有 0.09 个 minor**。这条耦合不能只当作升级清单里的一行字，必须是构建门禁：

`scripts/check-pnpm-engine.mjs`（新）——用 `ELECTRON_RUN_AS_NODE=1 <electron> -e "process.versions.node"` 读出实际 Node 版本，与闭包里 pnpm 的 `engines.node` 比较，不满足即失败。解析不了的 range 形态也要显式失败，不能默默放过。

### 4. 门禁扩展

| 脚本 | 内容 |
| --- | --- |
| `scripts/check-pnpm-engine.mjs`（新） | 见上 |
| `scripts/check-pnpm-runtime.mjs`（新） | 在打包可执行文件上跑 `pnpm --version`；再用 `pnpm add file:<fixture>` 做一次**离线**安装（不依赖网络，可进 CI） |
| `scripts/smoke-package.mjs`（扩） | 断言 `pnpm/bin/pnpm.mjs` 存在，**且 `artifacts/` 已被裁掉**——防止 prune 规则失效把 18 MB 悄悄塞回来 |
| `pack` / `dist` 链 | 插入 `check:pnpm-engine`、`check:pnpm-runtime` |

### 5. 文档

- `.github/workflows/runtime-upstream.yml` 隐式契约清单加一条：*pnpm 的 `engines.node` 是否仍被 Electron 的 Node 满足*（有门禁兜底，清单条目是给人看的说明）
- 架构文档补一段：客户端为什么带一个包管理器，以及它只服务于 profile 插件安装

## 三个已实测的约束

这三条都做过验证，**其中两条没有可用的缓解手段**，必须在发版前明确接受或另想办法。

### ① store 位置无法用环境变量迁移

实测 `npm_config_store_dir` **不生效**——设了之后 pnpm 仍然写 `C:\Users\...\AppData\Local\pnpm\store\v11`。

能改的途径只有 `--store-dir` 命令行参数或 `.npmrc`。但 `dsh plugin` 是 verbatim 转发，客户端插不进参数；而在 `<DSH_HOME>/profiles/<name>/` 写 `.npmrc` 会碰用户与官方 CLI 共享的目录。

**决定：接受 pnpm 默认位置。** 记为「客户端卸载不清理的一处足迹」写进文档。好处是：与用户日后自装的 pnpm 共享同一个 store，不重复占盘。

### ② `packageManager` 自切换，实测关不掉

若当前目录的 `package.json` 带 `packageManager` 字段，pnpm 会**切换到该字段指定的版本**——实测内置的 11.20.0 变成了 10.11.0。

尝试过的四种关闭方式**全部无效**：

- `npm_config_manage_package_manager_versions=false`
- `NPM_CONFIG_MANAGE_PACKAGE_MANAGER_VERSIONS=false`
- `--config.manage-package-manager-versions=false`
- 在 cwd 放 `.npmrc`

原因是这个配置键在 pnpm 11 的 `dist/pnpm.mjs` 里**根本不存在**（grep 无命中），该设置在 pnpm 11 已被移除或改名。

**现状与风险：** dsh 的 `initProfile` 写出的 profile manifest 不带该字段，所以默认状态是安全的。但只要用户往 `<DSH_HOME>/profiles/web/package.json` 里加了 `packageManager`，客户端 pin 死的 pnpm 就会静默让位给一个从网络下载的 pnpm——对一个把供应链看得很重的仓库（见 `pnpm-workspace.yaml` 里 `minimumReleaseAgeExclude` 那段注释），这不是可以默认忽略的。

**这是一个未决项，第二阶段发版前必须选一个：**

- (a) 接受并在文档里写明；
- (b) 在座位逻辑读 profile manifest 时顺带检测该字段，命中就在日志/连接面板里告警；
- (c) 继续查 pnpm 11 是否还有别的开关（本次没查到）。

### ③ `allowBuilds` 的残留缺口

pnpm 10+ 默认拦截未列入 `allowBuilds` 的生命周期脚本。**带 `prepare` 的 git 插件仍然装不上**，用户得手工编辑 `<DSH_HOME>/profiles/<name>/pnpm-workspace.yaml`——dsh CLI 已经打印了这条提示。

**不要自动放开 `allowBuilds`。** 那等于让一个刚下载、尚未审查的插件的 postinstall 无条件执行，与市场「先审查再安装」的整个设计直接冲突。保持现状。

因此准确的说法是：**第二阶段闭合的是「预构建 tarball」这一类插件**（恰好是目录里的主流形态，市场自己就是），不是全部。

## 验收

同样**必须在真实打包版上跑**。在 Agent 的 shell 里：

1. `pnpm --version` → 报的是闭包里 pin 的版本
2. `dsh plugin --profile web add <市场 tarball>` → 安装成功，`dependencies` 与 `dsh.profile.bundles` 都被 `reconcilePlugins` 更新
3. 重启客户端 → 插件实际加载，市场「已安装」面板能看到它
4. 客户端自带的 in-box 市场座位**未被误伤**（`.dsh-desktop-seat.json` 仍在，`bundles` 里的条目仍在）
5. 机器上装有用户自己的 pnpm 时，`pnpm --version` 报的是**用户那份**（验证追加而非前置）
6. 打包产物里 `pnpm/artifacts/` 已被裁掉
7. 断网状态下 `pnpm --version` 不尝试联网
8. 装完插件后 `ELECTRON_RUN_AS_NODE` 没有泄漏进任何子进程（沿用 `check-runtime-env.mjs` 的断言方式手验一次）

# 平台兼容性：macOS

整体兼容——两个阶段都不需要 macOS 专属的设计分支。但有 4 处必须显式处理，其中第 3 条**不能用 Windows 的实测结论外推**。

## ① `process.execPath` 含空格（第一、二阶段）

macOS 打包后是：

```
/Applications/DeepSeek Harness Desktop.app/Contents/MacOS/DeepSeek Harness Desktop
```

计划里的 POSIX shim 已经用双引号包住 `<execPath>` 与 `<resources>`，正确；`ENV=v ENV2=v2 exec "..." "$@"` 的前缀赋值 + exec 形式是合法 POSIX sh，现有 node shim 就是这么写的。

这是 macOS 上最经典的 shim bug，**验收必须显式覆盖**——在 Windows 上永远暴露不出来。

## ② 登录 shell PATH 的时序（已核实，无需改动）

macOS GUI 应用继承的是 launchd 的精简 PATH，客户端用 `restoreMacGuiPath()` 从用户登录 shell 里恢复。核实过调用时序：

- `src/main/index.ts` 启动流程里 `const guiPathReady = restoreMacGuiPath()`
- 之后 `await guiPathReady` 才 `boot()`

所以 `childPath()` 读到的是**已恢复**的 PATH，shim 目录追加在它后面，顺序正确。

**但有一个推论要记住：** macOS 上用户自装的 `dsh` / `pnpm` 通常在 Homebrew 或版本管理器目录里，这些目录**只有靠 `restoreMacGuiPath()` 才会出现**。该探测有超时；一旦超时，用户自装的工具就看不见，客户端会用内置的那份。这不是本计划引入的问题（node shim 已经如此），但第二阶段会放大它的可见度：用户明明装了 pnpm，客户端却用了内置的。文档里要写明这一点。

## ③ pnpm 不是纯 JS —— macOS 必须单独实测（第二阶段）

pnpm 的 `dist/node_modules` 里带原生模块：

```
@reflink/reflink-darwin-arm64/reflink.darwin-arm64.node
@reflink/reflink-darwin-x64/reflink.darwin-x64.node
@reflink/reflink-win32-arm64-msvc/…
@reflink/reflink-win32-x64-msvc/…
```

**好消息：** 全平台二进制都 vendored 在同一个 npm 包里，不需要按 arch 分别安装——macOS arm64 与 x64 两个 dmg 可以用同一份闭包产物。（可选优化：按目标平台裁掉其余三份。）

**必须验证的：** 这些是 napi-rs 模块（N-API ABI 稳定，理论上兼容 Electron），但 Electron 的 `NODE_MODULE_VERSION` 与 stock Node 不同。本计划的 pnpm 实测是在 **Windows** 上做的，而 **reflink 在 NTFS 上基本不启用，APFS 却支持 clonefile**——也就是说 macOS 恰好是这条原生路径真正会被走到的平台，**Windows 的成功不构成 macOS 的证据**。

即使 reflink 加载失败，它只是「拷贝优化」，pnpm 应当降级为普通复制——但「应当」需要在 mac 上真跑一次 `pnpm add` 来确认，而不是假设。

## ④ 代码签名（第二阶段，风险低）

仓库是 ad-hoc 签名（`identity: "-"`）+ `hardenedRuntime: false`。往 `Contents/Resources` 里加带 `.node` 的包由 electron-builder 一并签名。

现有运行时闭包**已经**携带大量 darwin 原生模块（sharp / koffi / node-pty / ripgrep / node-addon-require-builtin 的 arm64 与 x64 两份），这条路已经走通，pnpm 的 reflink 只是多一个。风险低，但仍应在 mac 打包后确认 `codesign --verify` 通过。

## 一个既有的边角：`isSameDirectory` 与 APFS 大小写

`isSameDirectory()` 只在 win32 上做小写归一，darwin 走精确文本比较；而 APFS 默认**大小写不敏感**。所以用户若手工把 `~/.DSH-desktop/bin`（大小写不同的拼法）加进自己的 PATH，`findOnPath` 的排除会失效。

这是**既有行为**，node shim 时代就存在，不是本计划引入的。但计划让 `dsh` 也进了那个目录，失效后果变成：客户端把自己的 shim 当成「用户自装的 dsh」→ 探测阶段 `--version` 被网关放行、成功报出版本 → 真正启动时 `web --port …` 被网关拦截 → 运行时永不就绪。

**好在现有的 auto-fallback 会兜住**（`installedDshRejected` 之后本会话改用内置运行时），所以是可恢复的，只是难看。可选加固：`detectDshOnPath()` 对解析结果做一次 `realpathSync` 后再比对 shim 目录。

## macOS 专属验收

在 mac 打包版上补跑（不能只在 Windows 上验）：

1. `dsh --version` / `dsh --profile web --dump-config` → 正常（证明含空格的 execPath 被正确引用）
2. `dsh web` → 拦截文案 + 退出码 2
3. 第二阶段：`pnpm --version` 与一次真实的 `dsh plugin --profile web add <tarball>` → 成功（**这是 reflink 原生模块在 Electron ABI 下的唯一有效验证**）
4. 装了 Homebrew pnpm 的机器上，`pnpm --version` 报的是**用户那份**
5. `codesign --verify --deep` 对打包后的 .app 通过
6. arm64 与 x64 两个 dmg 都要跑，不能只验其中一个

## 实施顺序建议

第一阶段从 `dsh-cli-policy.ts` + `scripts/check-dsh-cli.mjs` 起手：策略表先钉死，后面的接线就没有争议了。

第二阶段从 `scripts/check-pnpm-engine.mjs` 起手：先把版本耦合变成红色构建，再往闭包里加东西——顺序反过来的话，一次 Electron 升级就可能在没有任何信号的情况下把 pnpm 变成硬失败。
