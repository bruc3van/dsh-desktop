# The desktop client — an independent Electron application over the dsh Web UI's public interface

[中文](desktop-client-architecture.zh.md)

## Problem

The `dsh` Web UI is the official product surface. The desktop client must remain an **independent third-party shell** with its own identity and connection settings while running real harness sessions. It therefore composes only public product boundaries: the `dsh` CLI starts a local Web UI when needed, and the window loads the Web UI origin directly. No internal harness package is imported.

## Decision

The client (this repository, `dsh-desktop`) has three runtime layers:

- **Electron main** (`src/main/`): owns the windows, Web UI runtime, and the desktop shell's in-app updater. The updater reads `latest.json` from the GitHub Release (written by the release workflow from the platform artifacts and SHA-256 sums), verifies the hash, and launches the matching installer. It does not use electron-updater, and electron-builder must not infer a publish provider. Feed and download both travel over Electron's `net.fetch` (credentials omitted), so they follow the system proxy, any PAC script, and the OS trust store — Node's own fetch honours none of those, which is how a machine could read the feed from one host and then fail the installer download on another with a bare `fetch failed`; Node's fetch remains the fallback, the reason behind such a failure is reported from the error's `cause` chain, and every update surface links to the releases page for a manual download. Unpackaged development builds do not auto-check. In **local mode** it probes the default loopback instance (plus any ports configured in the web profile's patch layer, `cordis.patch.yml`) and otherwise spawns `dsh web --port 0`; if the reused instance disappears, it falls back to the managed local runtime. When nothing answers the probe, it prefers a **user-installed dsh** over the bundled runtime, from two sources in order. First, `dsh` on PATH (excluding the client's own shim directory), verified by a `--version` run, which establishes both a working system Node behind its shebang and a bootable CLI. Second — and this is the one the official instruction actually produces, since `npx @deepseek-ai/dsh web` installs nothing onto PATH — a package npx has already cached, found by reading npm's cache root (`~/.npm/_npx` on POSIX, `%LOCALAPPDATA%\npm-cache\_npx` on Windows, `npm_config_cache` overriding both) and checking each entry's `package.json` for the `@deepseek-ai/dsh` identity before taking its declared bin and true version; the most recently touched matching entry wins. The cache is read rather than re-invoked through `npx`, which keeps the step offline and instant, and spawns the entry directly on the user's own Node with no wrapper process — on Windows that also avoids the cmd.exe layer a `.cmd` shim would introduce. Neither source installs or downloads anything, and an absent one is simply skipped; detection runs once per session, only on the branch that is about to start a runtime, and `DSH_DESKTOP_SKIP_INSTALLED_DSH=1` pins a run to the bundled closure. Such a child runs on the user's own Node, so it never receives `ELECTRON_RUN_AS_NODE` (a Windows `.cmd`/`.bat` wrapper is spawned through the platform shell, which the POSIX path never uses). An installed runtime that never reaches readiness is rejected for the rest of the session and replaced by the bundled one immediately, rather than spending the shared retry budget on the same failure. In **connect mode** it uses a configured Web UI origin, preserves that explicit choice on failure, and prompts instead of silently switching locally. In development, the command resolves from `DSH_DESKTOP_DSH`, a verified user-installed `dsh`, the pinned `@deepseek-ai/dsh` dependency, sibling checkouts, then PATH. Release packages must carry the official CLI's complete runtime closure; a missing closure is reported as a damaged installation instead of silently falling through to PATH. Child supervision provides bounded relaunch, retry-budget reset after a stable window, per-generation readiness, stale-callback rejection, and graceful shutdown (SIGTERM→SIGKILL on POSIX; `taskkill /T /F` on Windows). On Windows the tree walk must run **before** the direct child is terminated, never after: descendants — the harness's shell children, and the cmd.exe wrapper a user-installed `.cmd` shim is spawned through — are reachable only from a parent that is still alive, so killing the parent first orphans the server that holds the port. An uncaught exception or an explicit exit skips that ladder entirely, so a synchronous last-resort disposal (`taskkill /T /F` via `spawnSync` on Windows, `SIGKILL` elsewhere) also runs on process exit, and a closed stdout is prevented from turning the next log line into a fatal EPIPE. Packaged builds run the bundled CLI through Electron's Node mode (`ELECTRON_RUN_AS_NODE`), but do not boot the official bin directly: the child first loads `src/main/runtime-launcher.ts` (shipped outside app.asar, with the entry path passed through `DSH_DESKTOP_RUNTIME_ENTRY` so the harness's `process.argv` contract is unchanged). The launcher removes the Node-mode variable from the environment and re-attaches it at the spawn boundary for `process.execPath` targets only, so the two runtime paths that respawn Node — the native directory-picker worker and the Windows ACL sandbox runner — keep working while the Agent's own shells no longer inherit it. `scripts/check-runtime-env.mjs` pins that contract, and the package smoke re-runs the same contract on the packaged Electron binary. Packaged builds also publish Electron's Node as `node` in `~/.dsh-desktop/bin` and **append** that directory to the child's PATH, so a user's own Node keeps priority. Before that launch, packaged macOS builds merge a deadline-bounded shell PATH — an interactive login shell first (which reads `~/.zshrc`), falling back to a plain login shell — for later Agent subprocesses to inherit.
- **Window surface**: Electron paints a local loading document immediately after ready, then the same secure window loads the **official Web UI itself** at its origin. Session titles, controls, and all product interactions are therefore official behavior. The preload exposes a small connection bridge and may append a clearly marked connection card, an app-update block, and a DeepSeek key-help link to the official settings dialog. The repository does not maintain or build a second product renderer.
- **Bundled-plugin seam**: the client's runtime closure may carry a plugin (today, the plugin marketplace) and seats it the way the official in-box bundles are seated — `resolveBundleDir()` resolves `dsh.profile.bundles` entries from the dsh installation before the profile, and `dsh plugin` never touches a name that is not a profile dependency. Seating is therefore two steps: the plugin is **copied** into `<DSH_HOME>/profiles/node_modules`, and its package name goes into the profile's `dsh.profile.bundles`. Copying rather than linking is the entire reason the seam works across runtimes: Node resolves a package from its realpath, so a link into the closure made the plugin's `@deepseek-ai/*` imports resolve *inside* that closure — handing whichever runtime was serving a second copy of the Service classes it already ran. A real directory resolves upward through `profiles/node_modules`, which the harness heals on every boot with the dependency graph of the installation that is actually serving — exactly the path a plugin installed by `dsh plugin add` takes. The market is no longer a special case. Both steps are reversible in one, which is what makes the seat safe to take automatically: a plugin that throws while loading fails the WHOLE plugin tree. Every runtime the client **starts** is a candidate, not just its own; what gates them is a version check — the plugin is built against the dsh this client ships, so an older runtime (which may not export what it imports) is refused and a newer one is allowed. A runtime the client did not start (a reused instance, a pinned address) still releases the seat: not for safety, but because the client does not control its boot and cannot know when a change would take effect. The plugin guards itself too: its entry reaches the real body only through a guarded dynamic `import()`, so an incompatible runtime costs the market and nothing else. The user can turn the seat off in connection settings, and that choice is durable in the client's own settings (the seat is re-offered on every start, so an unrecorded removal would undo itself); once the client is uninstalled, the market's own installed panel is the only remaining way to remove it, which is what the copy's ownership marker is for. A missing closure copy drops the entry and the copy. A first-ever `DSH_HOME` has no web profile until the child creates it, so the seat is taken after readiness for the next start. A copy the user installed themselves as a profile dependency at a version no older than the closure is left entirely alone; a stale overlay is lifted (the dependency and the nearer profile install are removed). See `src/main/bundled-plugin.ts`.
- **Runtime lock**: two harnesses appending to one session store corrupt it permanently — each carries its own in-memory sequence numbers, so the log gains duplicate seqs and orphan inbox splices and the affected sessions never resume; and the client cannot discover every harness on the machine (the official web port comes from a `--port` flag OR from the profile's patch layer, which leaves nothing on the command line to find), so exclusion must not rest on discovery. What the client can do reliably is never run two of its OWN runtimes: it records the spawned child's pid, the desktop pid, the spawn time, and the served origin once ready in `.dsh-desktop-runtime.json` under `DSH_HOME` (written through a temp file and renamed — a torn read would parse as "no runtime", the one wrong answer that costs data). The next start reads the record first: a surviving process is adopted (same harness, sessions shared) instead of spawning beside it — that survivor is not hypothetical: a Windows installer that kills the app by name leaves the runtime child running, and the updated app would otherwise become the second writer on that `DSH_HOME`. The record is advisory and self-healing: a child that neither answers nor exists is cleared rather than obeyed, so a crashed client cannot wedge the next start; an unreachable leftover is cleaned up before restarting, and one that can be neither reached nor killed makes the client refuse to start, with a reason. The update path obeys the same constraint: the runtime is stopped only after the installer download and its SHA-256 verification succeed and immediately before the installer runs — a failed download or verification, or an installer that never launches, leaves the runtime intact or restores it (previously, on Windows, the installer killed the app by process name but not the `node.exe` runtime child, orphaning a writer on `~/.dsh`). See `src/main/runtime-lock.ts`.
- **Settings seam**: a private random-path loopback page provides the native connection window and writes `settings.json` under `~/.dsh-desktop`. It is not an API carrier and does not proxy `/api`, WebSockets, or renderer assets.

The client's own connection settings live in `~/.dsh-desktop` (override `DSH_DESKTOP_HOME`); the local child runs with the **official `DSH_HOME` (`~/.dsh`)** so conversations, titles, credentials, and model configuration are shared with the `dsh` CLI and the browser Web UI. The window wears the official logo (macOS template dock icon, Windows/Linux window icon) and a standard title bar (the official Web UI carries its own header). The credentials seam is used as-is: `DEEPSEEK_API_KEY` is set through the official UI's settings.

Development/diagnostic variables `DSH_DESKTOP_DSH` and `DSH_DESKTOP_NODE` override the CLI and Node paths. `DSH_DESKTOP_SKIP_PROBE=1` and `DSH_DESKTOP_PROBE_URL` are test-only probe controls, not user configuration surfaces.

The current release matrix covers separate macOS Apple Silicon and Intel packages plus Windows x64. Each native runner deploys only its current architecture. `dsh-runtime/package.json` retains Linux x64 native optional packages for source builds and future release re-enablement. The pinned Win32 native-picker package carries a client-owned, exact-version pnpm patch because its `koffi.view()` path aborts Electron's embedded Node while reading the selected COM path; the patch copies the exact UTF-16 bytes through Win32 instead and is verified against Electron during the Windows build. Adding a release architecture or upgrading dsh requires rechecking that list, reconciling or removing this patch, and running the package smoke on the corresponding platform.

## Consequences

- `pnpm run dev` builds and launches the client; `pnpm run shot` / `pnpm run audit` / `pnpm run e2e` drive Playwright-based verification. `pnpm run check:picker` verifies the deployed patch and, on Windows, its Unicode COM-path conversion under Electron's Node. `pnpm run smoke:package` launches the packaged app with an empty PATH, requires explicit bundled-CLI selection, and probes `host.describe`.
- The client works identically against a local `dsh web` or any reachable Web UI instance (the Web UI origin is the only coupling), on macOS, Windows, and Linux; local and probed modes show that instance's stock official UI. Official dsh currently targets local use only (`127.0.0.1` by default; the network-exposing `0.0.0.0` bind is rejected), so remote instances are outside official support.
- Sessions run the Web UI's composition (the official web profile) — content search, the `/` command and skill menus, background tasks, message actions (fork, feedback), plan-mode, pending-queue rows, agent presets, the permission selector, the goal chip, the model catalog, and session titles/renaming — because the interface IS the official web app.
- The model-visible orientation is set by the official web profile's own surface prompt (the "Web GUI" identity); the client adds nothing of its own.

## Alternatives considered

| Rejected | One-line reason |
|---|---|
| Compose many fine-grained harness packages directly (previous architecture) | The published `@deepseek-ai/dsh` CLI is a more stable and complete public runtime boundary |
| Maintain a second production renderer | It duplicates the official product surface and drifts from official behavior |
| Reverse-proxy `/api`, WebSockets, and assets through a desktop carrier | Loading the official Web UI origin directly is a smaller and more faithful boundary |
| Direct cross-origin `/api` calls from a custom renderer | There is no production custom renderer; the official page talks to its own origin |
| Run the harness inside the Electron main process | Electron's Node lags the engine range and native modules would need an Electron-ABI rebuild |
