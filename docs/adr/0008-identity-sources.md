# ADR-0008 身份源：登录与通讯录同步的统一模型

状态：已采纳（0.7.0-rc.1）

## 背景

国内企业的身份基本在飞书、钉钉或企业微信里。三家都不是标准 OpenID Connect：

| | 飞书 | 钉钉 | 企业微信 |
|---|---|---|---|
| 登录 | OAuth 2.0 + PKCE，另调用户信息接口；没有 ID Token | OAuth 2.0（回调参数叫 `authCode`），另调 `contact/users/me` | 自有的扫码/网页登录，回调后用应用凭证换 `userid` |
| 稳定的人员 ID | `union_id`（同一开发者的应用间一致） | `unionId` | `userid` |
| 限定到本企业 | 自建应用只在本企业可用；用户信息带 `tenant_key` | `scope=openid corpid` 时令牌响应带 `corpId` | 非本企业成员只拿到 `openid`，拿不到 `userid` |
| 邮箱 | 管理员导入、未经用户验证，官方文档说明不应作为登录凭据 | 个人填写 | 2022-06-20 后新建的自建应用不再返回 |
| 通讯录读取 | contact v3：部门子树、按部门列成员（含离职、冻结状态） | `department/listsub`、`v2/user/list`（离职的人直接不再出现） | `department/list`、`user/list`（状态 1/2/4/5，5 为已离职） |
| 实时变更 | 事件订阅，支持长连接（无需公网地址） | 事件订阅，支持 Stream 长连接 | 回调，需要公网 HTTPS、可信域名和可信 IP |

参考了 Authing 同步中心、Casdoor、NocoBase 的做法，以及 SCIM 2.0 的离职处理惯例。共同的教训：

- 用**不可变的外部 ID** 关联人，不用邮箱或手机号。用可变字段对账，迟早会停用错人或停用不掉该停的人。
- 离职是**停用**，可以恢复，不是删除；停用时要同时吊销会话和令牌，而不只是改一个状态。
- 一个组织只认**一个上游**作为人员的来源。
- 全量对账是事实来源，事件只是「有变化，快去看看」的提示。
- 防止误删：权限范围被改小、接口暂时返回空列表时，不能把全公司停掉。

Casdoor 的一个问题值得避开：它同步时存一种 ID、登录时用另一种 ID，于是第一次登录只能靠邮箱或手机号匹配，而且把这些字段当成已验证的。

## 决定

### 一个身份源 = 登录 + 通讯录

每个平台实现两个接口，服务端其余部分只认归一化后的结果：

- **登录**：`authorizeUrl()` 生成跳转地址，`complete()` 处理回调，返回 `{ provider, subject, name, email?, emailVerified }`。OIDC 也改用同一个接口。
- **通讯录**：`fetch()` 返回一份完整快照：部门 `{ externalId, name, parentExternalId }`，成员 `{ externalId, name, email?, active, departmentExternalId }`。字段形状对齐 SCIM 2.0（`externalId`、`active`、组织单元），以后接 SCIM 入站（Entra ID、Okta 推送）时不用改同步引擎。

登录返回的 `subject` 与通讯录的 `externalId` 是**同一个 ID**（飞书 `union_id`、钉钉 `unionId`、企业微信 `userid`），所以同步过来的人第一次登录就能直接对上，不经过邮箱。

### 一个组织一个上游

`DSH_DIRECTORY` 选定飞书、钉钉或企业微信之一。选中的平台同时提供登录。来自这个平台的成员**只能由通讯录产生**：平台登录不按邮箱匹配，也不自动创建成员。这同时解决了「限定到本企业」：不在本企业通讯录里的人，ID 对不上任何成员。钉钉另外校验令牌里的 `corpId`。

OIDC 和开发登录保持原样，可以与上游并存（例如 IT 用 Entra ID 登录控制台）。

### 同步 = 计划 + 应用

1. 拉取完整快照。
2. 与库里「由这个上游管理」的部门和成员比对，得出计划：新建、更新（姓名、邮箱、部门）、停用、恢复、认领、删除部门。
3. 应用计划：一个事务写库，配置版本只加一次；每个被停用的人走和手动停用完全相同的离职流程（结束会话、吊销所有设备的网关 Key、吊销设备）。

规则：

- **离职或从通讯录消失 → 停用**，不删除。重新出现时，如果当初是同步停用的，自动恢复；管理员手动停用的不恢复。
- **认领**：库里已有一个不受管理的成员、邮箱与通讯录里的人相同，就把他认领为受管理成员（保留角色、设备和历史）。认领只在同步时、以可预览的方式发生，不在登录时发生。
- **受管理的字段只读**：姓名、邮箱、部门由上游决定，控制台和 CSV 导入不能改；角色、停用、场景包仍由管理员决定。
- **一人多部门**：取主部门（企业微信 `main_department`），没有时取第一个。
- **防误停**：一次同步要停用的人超过受管理在职人数的 `DSH_DIRECTORY_MAX_DISABLE_PERCENT`（默认 20%，至少 3 人），或者会停用全部受管理的人时，整次同步不应用，记为「已拦截」，管理员预览后可以确认强制执行。
- **定时 + 手动**：每 `DSH_DIRECTORY_SYNC_MINUTES` 分钟（默认 15）一次全量对账；控制台可以预览和立即同步。每次运行都记录结果，停用、恢复、认领、新建都写审计。

### 暂不做

- **事件订阅**（飞书长连接、钉钉 Stream、企业微信回调）：作为「立刻对账一次」的触发器接入，不单独处理事件内容。在此之前，离职最晚在一个同步周期内生效。
- **SCIM 入站**：模型已对齐，等有 Entra ID / Okta 的客户再做。
- **一人多部门**与**部门负责人**：等场景包需要时再做。

## 放弃的方案

- **按邮箱关联**：飞书明确说邮箱未经验证，企业微信新应用拿不到邮箱。
- **登录时自动创建成员**：无法可靠地限定到本企业，也绕过了「人员只来自通讯录」。
- **逐条处理事件、不做全量对账**：事件会丢、会乱序；全量对账可以自愈。
- **三家各写一套同步逻辑**：比对、防误停、离职流程只写一次，平台只负责「读」。
