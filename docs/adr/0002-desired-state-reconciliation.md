# ADR-0002 期望状态文档 + 客户端对账

状态：已采纳

## 决定

组织对一个人的全部要求写在一份有版本号的 JSON 文档里（`packages/protocol` 中的 `DesiredState`）。文档可以来自 IT 放置的文件，也可以来自服务端，客户端用同一个对账器应用它。

对账器（`enterprise/reconcile.ts`）只改文件，并且是幂等的：
- 写在 profile patch 层**末尾的一个托管块**里，每次整块重写。手改的内容会被恢复（漂移恢复）；因为托管块在最后，会覆盖用户或官方界面写在前面的同名条目。
- 凭据写进 DSH 自己的凭据文件 `refs`，Skill 写进带标记的目录，组合包写进 profile 清单。客户端加过哪些东西记录在账本 `.dsh-desktop-pro-managed.json` 里，只撤回账本里有记录的。
- 每个部分单独尝试，失败的部分作为 problem 上报，不影响其他部分。

同一个对账器在两处运行：运行时启动前在 CLI 子进程里运行（首次启动时 profile 还不存在，要先 `initProfile()`），运行时启动后在主进程里运行（DSH 会监视 patch 层和凭据文件，大部分修改不用重启）。插件安装要用运行时自带的包管理器，所以在运行时就绪后通过 `dsh plugin` 执行。

`revision` 用租户级的配置计数器，单调递增：任何可能影响下发结果的修改都会让它加一，客户端不会退回到更旧的版本。

场景包合并时设置项以最具体的为准，**限制只会累加**：禁用的工具、禁止的插件取并集，离线宽限期取最小值。

## 放弃的方案

- **服务端推送指令（安装 X、卸载 Y）**：指令丢一条状态就错，而期望状态天然可以重试、自愈。
- **重新序列化整个 patch 文件**：会丢掉用户的注释、`!!js` 表达式和其他工具写的标记块。
- **通过运行中的 Web API 改配置**：多一层认证和版本耦合，首次启动时也没有服务可调。

## 修订（0.7.0-beta.3）：是否生效按设备算

原先「设备已生效」的判断是「设备上报的版本号等于组织当前的 `revision`」。`revision` 是全组织共用的计数器，任何人、任何地方的修改都会让它加一，于是加一个成员、改一个 Skill，所有设备都显示「等待同步」，每台都被唤醒重新拉取，各写一条审计。

现在把两件事分开：

- **`revision`** 只用来排序：客户端不接受比手里更旧的文档。仍然是租户级计数器，单调递增。
- **指纹（fingerprint）** 回答「这台设备该拿到什么」：这个人合并后的配置（去掉 `revision` 和 `issuedAt`）加上这台设备网关 Key 的签发时间，取哈希。服务端记录每台设备最近一次**下发**的指纹和最近一次**应用成功**的指纹。

由此：

- 设备「已生效」= 应用成功的指纹等于它现在该拿到的指纹。别人的变化不影响它。
- 长轮询只在这台设备该拿到的指纹与上次下发的不同时才唤醒它。
- 「下发」「应用」两类审计只在指纹或结果变化时记录，不再每次拉取都记。

指纹只在服务端计算和保存，不进签名文档，协议不变。
